# 十九、R18：Recall 与上下文组装

## R18-1：Recall 执行位置

**最终选择：方案 A——Local-first**

优先使用本地 Memory Replica 执行 Recall。

只有本地无法满足查询、缺少必要数据或需要远端补充时，才访问 Server。

降低远端查询延迟，并支持一定程度的离线使用。

## R18-2：记忆检索技术架构

**最终选择：方案 C——混合检索 + 实体关系扩展**

采用多种检索方式组合：

- 全文检索。
- 向量语义检索。
- 结构化过滤。
- 实体匹配。
- 关系扩展。

不将单一向量检索作为唯一 Recall 机制。

按阶段实现，先建立可靠的基础检索，再增加实体关系扩展。

## R18-3：Recall 检索流水线

**最终选择：方案 B——多阶段检索 + 可选模型重排**

Recall 采用多阶段处理：

1. 解析查询。
2. 根据上下文和权限确定检索范围。
3. 执行多路检索。
4. 合并候选结果。
5. 去重和过滤。
6. 必要时使用模型重排。
7. 生成最终结构化记忆结果。

模型重排是可选能力，不要求每次 Recall 都调用 LLM。

## R18-4：Pinned Memory 作用域

**最终选择：方案 C——Global + Project + Host + Session**

Pinned Memory 支持四个作用域：

- Global：跨项目通用知识。
- Project：项目相关记忆。
- Host：特定 AI Host 的工作习惯和上下文。
- Session：当前会话需要持续保持的上下文。

不同作用域需要明确优先级和授权边界。

## R18-5：Dynamic Projection 生成与更新

**最终选择：方案 C——基线 Projection + 动态增量更新**

先生成稳定的基线 Projection。

随着项目、Session 和任务上下文变化，再动态生成增量内容。

不要求每次发生变化都重新计算全部 Projection。

## R18-6：Context Budget 与 Token 分配

**最终选择：方案 C——分层预算 + 动态调整**

上下文预算分层管理。

根据记忆重要性、作用域、任务相关性和当前 Token 限额动态调整。

优先保证关键记忆和必要约束。

不能因为大量低价值记忆挤占预算而丢失关键工程知识。

## R18-7：Recall 输出格式

**最终选择：方案 C——结构化记忆 + 自然语言呈现**

Recall 内部保留结构化数据。

向工作模型提供便于理解的自然语言内容，同时保留：

- Memory ID。
- 来源。
- 可信度。
- 适用条件。
- 版本状态。
- 相关关系。

不将结构化数据和自然语言表达割裂。

## R18-8：模型遵循与反馈闭环

**最终选择：方案 C——注入 + 行为评估 + 反馈闭环**

不仅负责把记忆注入模型上下文，还要评估模型是否实际使用了相关记忆。

通过行为评估和反馈机制持续改善：

- Recall 结果质量。
- 注入内容。
- 记忆选择。
- 运行时提示。
- 记忆使用策略。

不把提示词注入本身当作模型遵循的保证。
