MnemoWeave：

- 生命周期治理。

R20-4：方案 C。

Contract-first，统一 Schema 驱动。

共享 TypeScript 契约，分别映射 HTTP/OpenAPI 和 MCP Schema。

# 二十一、R20：工程化与可靠性

## R20-1：核心模块依赖架构

**最终选择：方案 B——领域模块化 + 分层依赖**

按业务领域组织模块。

每个模块内部再划分 Domain、Application、Ports 等职责。

模块之间通过明确契约交互。

不采用无边界的传统分层混合结构，也不在第一阶段采用动态插件化微内核。

## R20-2：Mnemon Provider 适配策略

**最终选择：方案 C——官方接口优先，能力缺口通过适配层解决**

优先使用 Mnemon 官方 API。

不直接依赖其内部数据库 Schema。

Provider 必须声明能力。

能力缺口优先通过：
- 组合已有官方接口。
- Mneme 自身治理层补足。
- 向上游提出能力增强需求。

解决。

## R20-3：数据所有权与职责划分

**最终选择：方案 C——记忆数据与治理数据分离**

Mnemon 负责正式记忆及其原生实体关系和检索能力。

Mneme 负责：

- Candidate Memory。
- 审核记录。
- Provenance 扩展。
- Task / Pipeline Run / Receipt。
- 同步状态。
- 生命周期治理。

Revision 快照和当前版本指针的最终权威需要在详细设计中确定。

## R20-4：HTTP / MCP 接口契约管理

**最终选择：方案 C——Contract-first，统一 Schema 驱动**

以统一 TypeScript Schema 作为契约源。

HTTP 映射为 OpenAPI。

MCP 映射为工具 Schema。

Application Core 仍然是唯一业务执行入口。

## R20-5：任务与 Pipeline 故障恢复

**最终选择：方案 B——持久化状态机 + 检查点 + 自动恢复**

任务状态、执行阶段、检查点、重试次数和错误信息持久化。

服务重启后恢复未完成任务。

无法自动恢复的任务进入人工介入状态。

## R20-6：本地副本同步一致性

**最终选择：方案 C——快照初始化 + 增量批处理 + 定期校验**

首次通过一致性快照建立本地副本。

后续采用增量批量同步。

数据和 Cursor 在同一个本地数据库事务中提交。

定期全量校验，不一致时修复或重建。

支持 Tombstone、授权撤销、游标失效和索引修复。

## R20-7：安全与权限架构

**最终选择：方案 B——Bridge 身份 + Host 身份 + 作用域授权**

Bridge 拥有独立身份和凭据。

每个 AI Host 拥有独立身份。

Host 通过本地 Bridge 注册和认证。

Bridge 通过独立凭据连接 Server。

支持独立撤销、凭据轮换、TLS 和授权审计。

遵循 R7 Strict Grants。

## R20-8：配置管理与运行诊断

**最终选择：方案 B——结构化配置 + 统一诊断体系**

配置采用分层管理：

- 默认配置。
- 配置文件。
- 环境变量。
- 启动参数。

启动时执行 Schema 校验。

诊断覆盖：
- 结构化日志。
- Health Check。
- Readiness Check。
- Worker 状态。
- Task Queue 状态。
- Provider 状态。
- 同步延迟和 Cursor。
- 数据库和 Blob 状态。
- Model Gateway 状态。
- Trace ID。

预留 OpenTelemetry。

## R20-9：测试架构

**最终选择：方案 B——分层测试体系**

包括：

- Unit Test。
- Integration Test。
- Contract Test。
- E2E Test。
- Reliability Test。

选择性吸收属性测试、模糊测试、并发压力测试和故障注入。

重点保证 Provider、同步、任务恢复和多模块交互的可靠性。

## R20-10：数据迁移与软件升级

**最终选择：方案 B——版本化 Migration + 自动备份 + 恢复**

Mneme 和 Bridge 分别管理数据库 Migration。

重要升级前执行备份。

Migration 版本化管理。

升级失败时禁止进入正常业务状态。

优先向前修复，不依赖复杂的自动降级脚本。

Mnemon 内部数据库迁移由 Mnemon 自己负责，Mneme 不直接修改其内部 Schema。

## R20-11：部署与进程管理

**最终选择：方案 B——Server 系统服务 + Bridge 用户级后台进程**

Server：
- Linux 原生部署。
- systemd 管理。
- Worker 暂时在 Server 进程内部运行。

Bridge：
- Windows 用户级后台进程。
- Linux systemd --user。
- 多个 Host 共用一个 Bridge。

预留统一服务管理抽象，但第一阶段不额外建设复杂的跨平台服务管理体系。

## R20-12：组件版本兼容

**最终选择：方案 C——SemVer + Capability Negotiation**

所有组件独立版本管理。

连接时协商协议版本和能力。

覆盖：
- Server。
- Bridge。
- Adapter SDK。
- Host Adapter。

能力声明不代表获得授权。

必需能力缺失时明确拒绝相关功能，不允许静默降级造成数据不一致。
