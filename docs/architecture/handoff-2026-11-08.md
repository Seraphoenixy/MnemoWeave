# 第一部分：项目背景与目标

## 1.1 项目定位

Mneme 是一个独立的 AI Agent 记忆编排系统。

它不是重新开发一个记忆数据库，而是在成熟记忆后端 Mnemon 之上构建统一的记忆编排、治理、检索、上下文注入和多客户端接入能力。

核心目标：

1. 让不同 AI Host 共享统一的长期记忆。
2. 让工作模型能够主动读取、更新和沉淀记忆。
3. 通过后台整理和候选审核提高长期记忆质量。
4. 实现跨项目工程知识的抽象与复用。
5. 通过本地记忆副本实现低延迟 Recall。
6. 通过统一编排层解决不同客户端的记忆注入和行为遵循问题。
7. 支持未来扩展更多 AI Host 和记忆 Provider。

Mneme 的核心价值是记忆编排，而不是重复实现 Mnemon 已经提供的存储、图索引和检索能力。

## 1.2 项目背景

此前使用 dsh-mnemon 时发现两个问题：

- 长期记忆沉淀不够理想，一些值得长期保存的知识被归入项目档案，而没有进入真正的长期记忆空间。
- 即使已经通过插件和 Hook 注入运行时记忆，模型有时仍然不能很好地遵循。

因此，决定独立开发 Mneme。

采用 Mnemon 作为底层记忆系统，参考 dsh-mnemon 的 Source / Strategy / Enhancement / View 架构，重新设计统一编排层。

## 1.3 当前使用的 AI Host

目前使用：

- DSH（DeepSeek Harness）
- Codex
- ZCode

不再以之前使用过的其他客户端作为当前主要目标。

后续可以扩展，但第一阶段只需要完成上述三个 Host。

## 1.4 明确的非目标

- 不重新实现完整记忆数据库。
- 不把 Mnemon 的数据库当成可随意读写的内部数据源。
- 不要求每个 AI Host 独立运行一套完整记忆系统。
- 不依赖 Docker。
- 不强制购买第三方记忆服务。
- 不要求记忆 Provider 自己寻找额外 LLM 进行推理。
- 不在第一阶段实现复杂的第三方插件生态。
- 当前不考虑 Ygdria 集成，个人知识管理和个人知识沉淀仍由用户自行管理。

## 2.2 部署约束

明确禁止使用 Docker 作为部署前提。

Server：

- 运行在自部署 Linux 服务器。
- 原生安装和运行。
- 使用 systemd 管理。
- Worker 暂时运行在 Server 模块化单体进程内部。

Bridge：

- 部署在用户本地电脑。
- Windows 使用用户级后台进程。
- Linux 使用 systemd --user。
- 多个 AI Host 共用一个 Bridge。
- 本地维护 SQLite Memory Replica。

## 2.3 部署架构

```text
Remote Linux Server
│
├── Mneme Server
│   ├── HTTP API
│   ├── MCP Server
│   ├── Application Core
│   ├── Pipeline
│   ├── Task Workers
│   ├── Synchronization
│   ├── Model Gateway
│   ├── Provider Adapter
│   └── SQLite + Blob Store
│
└── Mnemon
    ├── Native Go Binary
    ├── SQLite Memory Store
    └── Native Recall / Remember / Link
          │
          │ 定期同步
          ▼
Local Windows / Linux
│
└── Shared Bridge
    ├── Host Authentication
    ├── MCP Gateway
    ├── Local HTTP Gateway
    ├── Local SQLite Replica
    ├── Local Recall
    ├── Dynamic Projection
    └── Synchronization
          │
          ├── DSH Adapter
          ├── Codex Adapter
          └── ZCode Adapter
```

本地数据库应当具备与远端权威记忆相一致的逻辑数据，使 Recall 优先在本地完成，减少远端查询时延。

注意：逻辑数据一致不代表 Mneme Server 与 Bridge 必须使用完全相同的物理数据库 Schema。Bridge 可以拥有必要的本地索引、同步元数据和运行状态。

# 第三部分：架构决策记录（ADR）

以下决策均为用户已经明确确认的最终选择，不得在实现过程中擅自更改。

## 3.1 P0 基础架构决策：ADR-001 至 ADR-006

| ADR | 决策主题 | 最终选择 |
|---|---|---|
| ADR-001 | 主开发语言 | TypeScript |
| ADR-002 | 核心部署形态 | 模块化单体 |
| ADR-003 | 记忆来源架构 | 完整继承 Source / Strategy / Enhancement / View |
| ADR-004 | 记忆沉淀策略 | 主动 Remember + 后台自动整理 |
| ADR-005 | Session 事件保存 | 选择性保存消息和重要工具事件 |
| ADR-006 | 扩展系统 | 第一阶段内置模块，预留 SDK |

补充约束：

- 不能把所有会话原文无限期保存。
- 记忆沉淀和普通事件保存必须区分。
- 后台整理不能直接绕过候选审核。
- 模块化单体不等于没有模块边界。

## 3.2 R1-R5：核心组件与规划机制

### ADR-007：R1 HTTP + MCP 双接口

选择方案 C。

HTTP 和 MCP 双接口：

- HTTP：生命周期事件、Session 上传、View、任务管理等。
- MCP：Recall、Remember、Link、Forget 等记忆业务工具。
- 两者共享业务逻辑，不允许分别实现两套记忆业务。

### ADR-008：R2 核心组件架构

选择方案 B：继承抽象，重新组织核心职责。

保留：

- Source
- Strategy
- Enhancement
- View

核心组件：

- Composition Core
- Registry
- View Composer / Validator
- Workers

Pipeline 作为底层可复用执行机制。

### ADR-009：R3 Strategy 与 Core 的职责边界

选择方案 B：Strategy 声明计划，Core 负责执行。

最终职责：

| 组件 | 职责 |
|---|---|
| Strategy | 生成 Composition Plan |
| Core | 校验 Plan，负责执行协调 |
| Pipeline | 执行具体任务 |
| Source | 提供记忆数据及操作能力 |
| Enhancement | 扩展标准能力 |
| View Composer | 生成最终 View |

Strategy 不直接越权执行底层操作。

### ADR-010：R4 Source / Provider 架构

选择方案 B。

Capability 是 Source 声明的标准能力契约。

Provider 不应成为任意业务逻辑的容器，而是通过 Source 暴露标准化能力。

### ADR-011：R5 规划机制

选择方案 D。

LLM Planner 按需调用：

只有规则无法充分确定执行方案时，才调用 LLM Planner。

不能让所有普通 Recall 和 Remember 都依赖 LLM Planner。

## 3.8 R19：记忆提炼、写入与知识质量

### ADR-025：R19 完整决策

R19-1：方案 B。

显式 Remember + 工作事件触发。

事件只是提炼素材，不直接写入正式记忆。

R19-2：方案 C。

固定一级知识类型 + 自由标签 + 实体关系。

初始知识类型：

- Concept：技术原理
- Practice：工程实践
- Architecture：架构决策
- Troubleshooting：故障案例
- Constraint：技术约束
- Procedure：操作流程
- Reference：技术参考

R19-3：方案 C。

跨项目知识抽象形成候选，经审核后晋升 Global。

保留原项目记忆及来源关系，不允许无依据泛化。

R19-4：方案 B。

结构化 Provenance + 可信度信息。

包含：

- Source
- Source Reference
- Evidence
- Verification Status
- Confidence
- Applicability
- Limitations
- Last Verified

模型自评置信度不等于实际技术验证。

R19-5：方案 C。

规则检查 + LLM 语义检查。

规则负责确定性检查，LLM 负责语义完整性、歧义和适用条件判断。

LLM 审核通过不代表技术结论已经验证。

R19-6：方案 B。

独立记忆 + 显式关系。

支持：

- Supports
- Contradicts
- Supersedes
- Refines
- DuplicateOf
- DerivedFrom
- RelatedTo

合并生成新候选，原始记忆不直接覆盖。

R19-7：方案 B。

Transactional Outbox + 稳定幂等键 + Receipt + Provider 结果核对。

Mneme 和 Provider 不假设存在共同事务。

R19-8：方案 C。

时间 + 事件双重触发重新验证。

知识状态区分：

- Valid
- ReviewDue
- SuspectedStale
- Superseded
- Invalidated

复核不等于失效，不能在验证之前删除正式知识。

## 3.9 R20：工程化与系统可靠性

R20-4：方案 C。

Contract-first，统一 Schema 驱动。

R20-5：方案 B。

持久化状态机 + 检查点 + 自动恢复。

快照初始化 + 增量批处理 + 定期校验。

Bridge 身份 + Host 身份 + 作用域授权。

R20-8：方案 B。

结构化配置 + 统一诊断体系。

### ADR-026：R20 第三批

R20-9：方案 B。

分层测试体系：

- Unit
- Integration
- Contract
- E2E
- Reliability

选择性吸收属性测试、模糊测试、并发压力和故障注入。

版本化 Migration + 自动备份 + 恢复。

Server 系统服务 + Bridge 用户级后台进程。

R20-12：方案 C。

# 第四部分：当前上游项目及技术核查

## 4.1 官方 Mnemon

仓库：

https://github.com/mnemon-dev/mnemon

官方文档：

https://mnemon.dev/

当前公开资料显示：

- Go 原生可执行程序。
- Go 1.24+。
- SQLite WAL。
- 单一 Mnemon 可执行文件。
- Node.js/npm 主要承担安装和启动器职责。
- 核心操作包括 remember、link、recall、forget、gc。
- 四图模型：Temporal、Entity、Causal、Semantic。
- LLM-Supervised：工作模型负责判断，Mnemon 负责确定性存储、图索引和检索。
- Embedding 可选，支持 Ollama 和 OpenAI 兼容接口。
- 提供本地 Web 工作空间。
- Agency Preview 是独立能力，不能与 Memory 核心混淆。

重要：目前不能假设 Mnemon 已经提供符合 Mneme 需求的通用远端 HTTP API。

`mnemon web` 是本地 Web 工作空间，也不能直接认定为正式业务 API。

必须从真实源码和 CLI 接口核查。

## 4.2 dsh-mnemon

仓库：

https://github.com/omdsh-dev/dsh-mnemon

这是 Mneme 的主要架构参考项目。

其核心抽象：

- Source：拥有记忆来源和操作能力。
- Strategy：决定哪些 Source 参与当前轮次以及如何组合。
- Enhancement：通过标准插槽扩展策略。
- Core：校验组合结果。
- View：不可变的本轮执行上下文。
- Host：负责绑定 View 和控制工具访问。

它提供多种 Memory Source、Strategy、Enhancement 和 Provider SDK。

但必须明确：

**dsh-mnemon 是 DSH 侧的编排和集成实现，不等于 Mnemon 官方引擎本身提供的能力。**

特别注意：

- DSH Host RPC 不等于通用外部 SDK。
- DSH Task Agent 不等于 Mnemon 内置 LLM。
- DSH 的 Source/Strategy/View 能力不应直接全部归属于 Mnemon。
- 第三方 Provider 的能力差异需要独立评估。

## 4.3 Provider Capability Matrix

必须对以下能力逐项核查：

| 能力 | 需要核查的内容 |
|---|---|
| Memory CRUD | 创建、读取、更新、删除 |
| Remember | 内容写入、去重、结果返回 |
| Recall | 关键词、语义、图关系检索 |
| Link | 关系创建和查询 |
| Entity | 实体管理 |
| Relation | 关系类型和关系操作 |
| Store | 多记忆空间管理 |
| Source | 数据来源管理 |
| Strategy | 是否属于上游或编排层 |
| Enhancement | 是否属于上游或编排层 |
| View | 是否支持不可变上下文 |
| Revision | 历史版本和当前版本指针 |
| Provenance | 来源和证据管理 |
| Change Feed | 增量变更流 |
| Snapshot | 一致性快照 |
| Tombstone | 删除传播 |
| Embedding | 向量生成和检索 |
| Search | FTS、向量、混合检索 |
| Capability | 能力声明和版本管理 |
| API | CLI、MCP、HTTP 的实际支持范围 |

每一项必须标注：

- 已证实支持。
- 部分支持。
- 未发现或不支持。
- 待进一步验证。

并记录：

- 仓库 commit。
- 文件路径。
- 函数、类型或接口名称。
- 必要时记录行号。
- 测试证据。

禁止仅凭 README 的功能介绍就认定具体接口已经存在。
