# 记忆活动记录与同步

活动区分「手动保存」和「自动沉淀」。手动保存包括让任务 Agent 处理候选和直接保存到指定目标。后台没有可写目标时也会记录一条跳过事件，包含结构化原因和零提交数。列表按事件发生时间排序，同步到本机的文件时间不参与排序。已有活动仍可读取，旧事件没有触发来源时显示原操作。同步客户端与服务端应一起更新，以识别新增事件字段。

记忆活动用于评估系统的读、写和委派效果。用回合与子任务关联键可以追踪一次召回是否返回候选、子 Agent 是否完成、以及写入是否收到持久提交回执。统计时区分没有命中、预算跳过、执行失败和结果未知。召回结果表示工具返回的证据，模型实际是否采用仍未知。

## 查看

工作台状态页的**记忆活动**列出最近记录的事件，最新的在前：发生时间、所属活动流、来源与操作、结果，以及返回条数、耗时或已提交写入数。跳过的读取另标原因。列表合并所选工作区的活动流与全局工作准则活动流，读取的是同一批不可变事件文件，因此同步后与另一台机器看到的内容一致。它只呈现结构化字段，不含正文、查询词、路径或错误原文，也不推断模型是否采用了召回结果。页面读取上限为 100 条，默认显示 50 条，每 5 秒重读一次。

回合级的记忆活动仍显示在对话末尾的记忆条上，按回合展开工具与条目；状态页这一区按时间排列事件，覆盖没有对话页的 MCP 工作准则活动与后台子任务。

## 删除记录

列表右侧的**删除活动记录**删除所选工作区的活动流与全局工作准则活动流当前已有的全部记录，不只是页面上列出的条目；确认后立即执行并重读列表。记录是被删除，不是被隐藏：旧活动读过一次就不再有用，留着只会让每次清理的成本高于它要解决的问题。

每个活动流在删除后只保留一条清空事件，记录该流现在从哪一刻开始。删除本身不逐条列名，因此一次清理只产生一个小事件，而不是与被删记录等量的清单。

清空事件随活动同步一起传输：服务端收到后丢弃被它取代的批次，只留下这条边界，因此服务端不会因为清理而变大；另一台机器收到后同样删除它自己保存的这些事件。未同步前只有执行删除的客户端不再显示这些记录。只读模式（`writeEnabled: false`）下删除与其他 mutation 一样在 Host 边界拒绝。

清理之后产生的活动照常记录与显示；记忆内容、会话历史、工作准则和已经执行的操作都不受影响。

<a id="activity-采集边界"></a>

## 采集边界

| 事件 | 来源 | 记录 |
|---|---|---|
| 召回、关联遍历和档案检索 | DSH 会话中配对的命名记忆工具调用和结果，MCP 的工作准则读取 | 来源、操作、结果条数、有限的条目引用、是否重放既有证据、跳过原因、结果状态 |
| 写入 | DSH 工具结果及其提交回执，MCP 的本机写入结果 | 操作、记录引用及已提交、跳过、未确认或失败状态 |
| 子 Agent | MnemoWeave 委派协调器的实际运行结果 | 父会话、回合、子会话、任务类型、终态、耗时、可取得的 token 用量 |

工作区使用自身的活动目录。即使 DSH 共用一个记忆数据根，不同工作区也按工作区标识分开。MCP 的工作准则读写归入单独的全局活动流。新记录随操作产生，无需重扫历史会话。DSH 接续的子会话仅采集本次会话实际执行的回合。

DSH 在回合结束后保存工具活动，委派协调器在运行收尾时保存子任务活动。缺少终态、时间或用量时会标为未知或省略对应字段。工作台直接预览、后台 Provider 内部操作及完整子会话仍使用各自的记录。被排除的工作区不采集 DSH 活动。

## 本地存储

活动记录为版本化 JSON，按事件 ID 各存一份，原子发布后视为不可变。DSH 工具事件的 ID 从会话与调用身份确定，重复接收同一回合可去重。MCP 调用和委派运行使用独立运行 ID。会话及条目引用只保存稳定摘要，记录不含正文、查询词、路径、提示词、工具参数、原始错误、工具输出或凭据。记录失败会报告固定错误，记忆操作仍以自己的工具回执为准。删除记录是本机唯一会移除事件文件的操作，它与一条清空事件一起发生。

工作区文件位于当前数据根的 `state/activity/workspaces/<workspace-id>/events/`。MCP 全局活动位于 `working-rules/state/activity/events/`。可以直接读取这些 JSON 文件做离线分析。活动目录与记忆 Pack 独立，导入或替换 Pack 不会改动活动。

## 同步

DSH 的 **记忆系统 → 设置 → 存储 → 服务器同步 → 同步全部** 会同步已登记且未排除的工作区活动，以及全局工作准则活动。MCP 配置同步服务后，在工具读写时尝试同步全局工作准则活动。活动通过 PAKE 会话和变更批次接口追加，使用独立于记忆快照的 scope。

客户端下载并验证活动批次，先合并不可变事件，再保存游标。上传仅提交在本机产生且当前目标尚未确认的事件，以事件 ID 为记录键。更改同步目标时，从旧目标拉取的事件仍留在本地历史中。发生游标冲突时，先拉取新提交，再计算仍需上传的条目。重试、进程重启和两台机器分别追加都保留已上传的活动。缺少回执的上传会通过重放远端日志确认。

服务端在写入批次的同一事务里登记事件 ID，并拒绝覆盖；唯一允许缩小活动流的是清空批次，它在同一事务里丢弃被取代的批次。被丢弃的批次不保留墓碑，所以清理确实减少了服务端占用。旧游标因此可能落在现存批次之前：活动流的 pull 允许这种间隔，读取方从现存批次继续，直到到达 head。

升级需要部署支持活动事件校验的同步服务，并更新发起同步的 DSH 或 MCP。现有记忆同步范围、快照格式和游标可继续使用；旧版服务端不认识清空事件，会把清理后的批次判为无效并返回 HTTP 400，此时该活动流停止同步，直到服务端更新。

每批最多 128 条上传记录。活动流只在手动删除时缩短，没有自动保留期，也不从原始 DSH 会话回填。远端可读取已同步的结构化记录。同一服务器上的 DSH 工作区名称仅在同步同一个工作区时复用。

活动记录按事件 ID 合并，因此同名工作区在两个客户端上的活动本来就是并集，不需要额外处理：事件不可变，两边新增的事件互不覆盖。与之配套的工作区记忆快照现在也按同名等价合并，见[服务器同步与部署](sync.md#ops-服务器同步)。
