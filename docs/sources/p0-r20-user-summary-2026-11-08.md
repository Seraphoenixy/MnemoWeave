# Mneme 全量架构决策选项汇总
**范围：P0 – R20**

**用途：** 项目架构基线、ADR 整理、Work 开发上下文。

**说明：** 本文以用户最终确认的选择为准。已恢复的方案描述按照完整决策含义整理；不能恢复原始评审措辞的部分明确标注，不将推测内容伪装成历史原文。

---

# 一、P0：基础架构决策

## P0-1：主开发语言

**最终选择：TypeScript**

Mneme 以 TypeScript 作为主要开发语言。

要求：
- 核心业务逻辑使用 TypeScript。
- Server、Bridge、协议层、Adapter SDK 和客户端插件尽可能共享类型定义。
- 使用严格类型检查。
- 统一管理依赖和构建流程。
- 允许调用 Go 等语言编写的外部程序，但不改变主开发语言决策。

## P0-2：核心部署形态

**最终选择：模块化单体（Modular Monolith）**

Mneme Server 采用单体部署，但内部通过明确的业务模块和接口进行组织。

各模块可以独立开发、测试，具有明确的职责和依赖边界。

不采用：
- 第一阶段即拆分微服务。
- 所有功能混合在一个无边界的代码模块中。

这样既降低部署和运维复杂度，又保留未来拆分的可能性。

## P0-3：记忆来源架构

**最终选择：完整继承 Source / Strategy / Enhancement / View**

参考 dsh-mnemon 的核心抽象。

- Source：定义记忆来源以及能够提供的能力。
- Strategy：决定本轮执行采用哪些 Source，以及如何组合。
- Enhancement：通过标准扩展点增强策略和处理能力。
- View：经过组合、校验后形成不可变的运行时记忆视图。

Mneme 不应将这些抽象简单合并为一个 Memory Provider。

需要保留来源、策略、增强和最终视图之间的职责区别。

## P0-4：记忆沉淀策略

**最终选择：主动 Remember + 后台自动整理**

采用两条记忆沉淀路径：

1. 主动 Remember：工作模型发现有长期价值的知识时，主动提交记忆。
2. 后台自动整理：根据保存的工作事件，定期分析、提炼并形成候选记忆。

后台整理不直接绕过审核机制写入正式记忆。

## P0-5：Session 事件保存

**最终选择：选择性保存消息和重要工具事件**

不无限期保存完整会话历史。

根据事件的重要程度选择性保存：
- 有长期知识价值的消息。
- 重要工具调用及其结果。
- 关键技术决策。
- 重要错误及解决过程。
- 影响后续任务的工程信息。

普通对话和无价值的工具事件不应永久保存。

## P0-6：扩展系统

**最终选择：第一阶段内置模块，预留 SDK**

第一阶段优先保证核心能力和架构稳定。

Source、Strategy、Enhancement 等扩展机制先以内置模块实现。

在架构上预留 SDK，使未来可以开发第三方扩展，但不提前建设完整的动态插件生态。

# 二、R1：对外通信接口

## R1-1：HTTP / MCP 接口架构

**最终选择：方案 C——HTTP + MCP 双接口**

Mneme 同时提供 HTTP 和 MCP 两种接口。

HTTP 面向常规程序化调用、客户端通信、任务管理及同步等场景。

MCP 面向 AI Host，提供语义化记忆工具，使工作模型可以直接使用记忆能力。

两种接口共享统一的业务核心，不能分别实现两套记忆业务逻辑。

---

# 三、R2：核心组件架构

## R2-1：核心组件组织方式

**最终选择：方案 B**

保留 Source、Strategy、Enhancement、View 的核心抽象，重新组织为 Mneme 自己的核心组件体系。

不简单照搬 dsh-mnemon 的实现，也不完全重新发明一套抽象。

重点是明确：

- 组件注册。
- 组件能力声明。
- Strategy 组合。
- View 生成与校验。
- 统一执行机制。

## R2-2：底层 Pipeline

**最终选择：采用 Pipeline 作为执行机制**

Pipeline 作为可复用的底层执行机制。

用于组织多阶段任务，例如：
- Recall。
- Remember。
- Candidate 审核。
- 正式记忆写入。
- Projection 更新。
- 后台知识整理。

Pipeline 不取代 Strategy，也不取代 Application Core。

---

# 四、R3：Strategy 与 Core 的职责边界

## R3-1：Strategy 执行架构

**最终选择：方案 B**

Strategy 负责声明本轮需要执行的组合计划，Core 负责验证和执行协调。

具体职责：

- Strategy 根据当前上下文确定参与的 Source、Enhancement 和相关处理规则。
- Strategy 生成 Composition Plan。
- Core 检查 Plan 的合法性、能力声明和授权条件。
- Core 负责调用 Pipeline 执行计划。
- 最终由 View Composer 生成不可变 View。

不允许 Strategy 任意越过 Core 直接操作底层 Provider。

---

# 五、R4：Source / Provider 架构

## R4-1：Source / Provider 架构

**最终选择：方案 B**

采用统一 Source 抽象和 Provider 实现分离的设计。

Source 描述标准化的数据来源和操作能力。

Provider 负责将具体外部记忆系统适配为 Source 能力。

例如 Mnemon Provider 可以实现 Mneme 定义的 Source 契约。

## R4-2：Capability 定位

**最终选择：Source 声明的标准能力契约**

Capability 不是独立的业务逻辑容器。

它是 Source 对自身能力的标准化声明。

Core 根据 Capability 判断某个 Source 能否参与指定操作，避免对不同 Provider 的能力作出错误假设。

---

# 六、R5：规划机制

## R5-1：规划机制

**最终选择：方案 D**

采用规则规划与 LLM Planner 相结合的机制。

优先使用确定性规则完成常规规划。

只有当规则无法充分确定执行方案时，才按需调用 LLM Planner。

避免所有普通 Recall、Remember 都产生额外推理调用。

LLM Planner 负责处理规则难以确定的复杂组合和语义判断，最终执行仍受 Core、Pipeline、Capability 和 Grants 约束。

---

# 七、R6：Enhancement 架构

## R6-1：Enhancement 架构

**最终选择：方案 B**

Enhancement 采用标准化扩展架构，通过明确的插槽和能力声明参与执行流程。

不允许任意扩展直接修改核心业务状态。

Enhancement 必须遵循 Core 的执行和权限约束。

## R6-2：模型调用权限

**最终选择：declared**

模型调用权限必须由组件明确声明。

只有具备相应声明和授权的组件才能通过 Model Gateway 调用模型。

不能让所有 Source、Strategy 和 Enhancement 默认拥有模型调用权限。

---

# 八、R7：View 架构

## R7-1：View 结构

**最终选择：方案 B**

采用结构化 View。

View 不只是拼接后的自然语言提示词，而是承载本轮运行时上下文的结构化对象。

应能够表达：
- 记忆内容。
- 来源。
- 作用域。
- 优先级。
- 适用条件。
- 授权信息。
- 上下文预算。
- 相关元数据。

## R7-2：Grants

**最终选择：strict**

采用严格授权机制。

组件和 Host 必须在授权范围内执行操作。

不允许仅凭提示词或模型自我判断决定是否具有权限。

## R7-3：View 更新机制

**最终选择：immutable**

View 一经生成即不可变。

需要更新时，重新生成新的 View，而不是原地修改已经交付给工作模型的上下文。

这样便于追溯、验证和保证本轮执行的一致性。

---

# 九、R8：记忆组织和 Runtime

## R8-1：长期记忆沉淀架构

**最终选择：方案 B——候选记忆层，审核后写入 Mnemon**

正式记忆不直接接受所有来源的原始写入。

先形成 Candidate Memory，再经过审核和治理，最终写入 Mnemon。

这样可以将工作事件、记忆提炼和正式知识存储分离。

## R8-2：Runtime 组织方式

**最终选择：方案 C——Pinned + Dynamic Projection 混合**

Runtime 由两部分构成：

1. Pinned Memory：明确固定、需要持续注入的记忆。
2. Dynamic Projection：根据当前项目、Host、Session 和任务动态生成的上下文投影。

Pinned 保证重要上下文稳定存在。

Dynamic Projection 保证记忆能够随着当前工作变化。

## R8-3：Session 事件保留策略

**最终选择：方案 B——限期归档，重要事件长期保留**

Session 事件采用分层保留策略：

- 热数据：近期活动和当前任务需要的数据。
- 限期归档：具有一定参考价值但不需要永久保存的历史事件。
- 长期保留：具有重要工程价值、技术决策价值和复用价值的事件。

不采用无限期保存全部原始消息的方式。

## R8-4：长期记忆分类方式

**最终选择：方案 B——统一记忆库，按知识类型分类**

采用统一记忆库，不为每种知识类型建立独立的物理记忆数据库。

通过以下机制组织：

- 知识类型。
- 实体。
- 标签。
- 关系。
- 作用域。

项目、技术领域和平台通过实体及标签组织，而不是将每个领域强制拆成独立记忆库。

# 十、R9：审核与冲突处理

## R9-1：审核机制

**最终选择：方案 B——自动审核，异常候选人工介入**

采用自动审核为主、人工审核为辅的方式。

普通候选记忆通过规则和语义检查后可以自动审核通过。

存在以下情况时需要人工介入：

- 来源证据不足。
- 内容存在不确定性。
- 与已有记忆发生冲突。
- 涉及重要工程决策。
- 跨项目抽象或晋升 Global。
- 自动审核无法判断其正确性和适用范围。

审核通过和正式写入是两个独立阶段。

正式写入必须经过可靠任务流程，并记录执行结果。

## R9-2：冲突处理

**最终选择：方案 C——保留历史，通过版本和替代关系更新**

不直接覆盖或删除已有正式记忆。

根据冲突性质分别处理：

- 同一知识的演变：创建新版本，保留旧版本。
- 新方案替代旧方案：建立 Supersedes 关系。
- 适用条件不同：同时保留，明确适用范围。
- 真实事实冲突：保留双方，标记冲突，等待验证或人工处理。

Recall 默认优先返回当前有效记忆，但允许根据查询需要获取历史版本。

# 十一、R10：Model Gateway

## R10-1：Model Gateway 架构

**最终选择：方案 B——Task-oriented Model Gateway**

通过统一 Model Gateway 管理模型调用。

调用方不直接绑定具体模型服务商，而是根据任务类型申请模型能力。

Model Gateway 负责：

- 模型配置。
- 模型选择。
- 调用参数。
- 超时。
- 错误处理。
- 调用结果。
- 使用记录。

## R10-2：工作模型与后台模型关系

**最终选择：方案 2——工作模型优先，后台模型按需补充**

工作模型是记忆沉淀的主要决策来源。

工作模型可以主动 Remember，也可以根据工作内容提交记忆更新。

后台模型用于按需完成辅助处理，例如：
- 候选记忆质量检查。
- 知识抽象。
- 冲突识别。
- 自动整理。
- 语义分析。

后台模型不是独立的记忆大脑，不允许记忆系统脱离上游编排层自行寻找模型。

---

# 十二、R11：模型路由和失败处理

## R11-1：Model Routing

**最终选择：方案 C**

采用统一的模型路由机制。

模型选择由 Model Gateway / Routing 层统一管理，而不是散布在各个业务模块。

不同任务可以配置不同的模型要求，路由根据任务类型、能力、配置和可用性选择模型。

## R11-2：模型失败与降级

**最终选择：方案 C**

采用统一的模型失败处理与降级机制。

模型调用失败不应导致整个记忆系统不可用。

需要区分：

- 可以重试的临时错误。
- 模型服务不可用。
- 超时。
- 参数或权限错误。
- 模型能力不满足要求。

可根据任务重要程度采取重试、切换模型、延迟处理或转人工介入。

# 十三、R12：任务队列和 Worker

## R12-1：Task Queue

**最终选择：方案 B**

采用持久化任务队列。

任务不只存在于内存中，而是具有持久化状态，可以在进程重启后恢复。

## R12-2：Worker 部署

**最终选择：方案 B**

采用既定的 Worker 部署方案。

Worker 负责执行后台任务和 Pipeline。

与 R20-11 一致，第一阶段不将 Worker 拆分成独立微服务，而是运行在 Server 模块化单体进程内部。

## R12-3：重试与恢复

**最终选择：方案 C**

采用既定的重试与恢复方案。

任务需要支持失败重试、状态恢复和异常处理。

后续 R13 和 R20-5 进一步确定：

- Task / Pipeline Run / Receipt 独立关联。
- 稳定幂等键。
- 检查点恢复。
- 显式暂停和取消。
- 人工介入。

**历史原始方案定义待恢复：** R12 三项的具体 A/B/C 方案比较正文尚未完整恢复。

# 十四、R13：任务执行与可靠性

## R13-1：Task / Pipeline Run / Execution Receipt 关系

**最终选择：方案 B——三者独立，建立关联**

三者具有不同职责：

- Task：业务任务及其生命周期。
- Pipeline Run：一次具体的 Pipeline 执行。
- Execution Receipt：外部操作的执行凭据和结果记录。

三者不能合并为一张简单任务表。

## R13-2：数据库事务与任务入队

**最终选择：方案 B——Transactional Enqueue**

业务数据变更和任务入队需要在同一数据库事务中完成。

避免业务状态已经提交，但任务没有成功进入队列。

## R13-3：外部操作幂等性

**最终选择：方案 B——稳定幂等键 + Receipt + 结果核对**

外部操作必须具有稳定幂等标识。

执行前后通过 Receipt 和 Provider 结果核对判断操作状态。

不能因为请求超时就假设 Provider 没有执行成功。

## R13-4：任务暂停、取消和人工介入

**最终选择：方案 B——显式控制状态 + 检查点恢复**

任务支持：

- 暂停。
- 恢复。
- 取消。
- 检查点。
- 人工介入。

恢复任务时从最近有效检查点继续执行，并核对外部操作状态。

# 十五、R14：数据库和存储

## R14-1：Mneme 自身数据库选型

**最终选择：方案 A——SQLite 优先**

Mneme 自身采用 SQLite。

优先考虑自部署、低运维成本和单实例部署。

## R14-2：业务数据组织

**最终选择：方案 B——单数据库，按模块独立建表**

各业务模块共享同一个 SQLite 数据库。

不同模块独立拥有自己的数据表和数据访问边界。

不为每个业务模块建立独立数据库。

## R14-3：原始事件与大型内容

**最终选择：方案 B——数据库元数据 + 本地内容寻址文件存储**

SQLite 保存元数据、索引和文件引用。

大型原始内容放在本地内容寻址存储中。

通过内容 Hash 和引用关系管理文件，避免将大型内容全部直接存入数据库。

## R14-4：同步与备份

**最终选择：方案 C——完全依赖自部署服务器，不提供通用文件同步和备份机制**

不建设通用云盘、文件同步和用户云备份服务。

后续 R16、R17、R20 增加的记忆副本同步、增量变更和升级安全备份属于 Mneme 自身业务机制，不属于通用文件同步服务。

---

# 十六、R15：HTTP、MCP 与 Shared Bridge

## R15-1：HTTP / MCP 与业务核心的关系

**最终选择：方案 B——共享 Application Core，协议层独立**

HTTP 和 MCP 通过独立协议适配层进入同一个 Application Core。

不重复实现业务逻辑。

## R15-2：MCP 工具设计

**最终选择：方案 B——面向记忆业务的语义化工具**

MCP 工具直接表达记忆业务操作。

例如：

- Recall Memory。
- Remember Memory。
- Link Memory。
- 查询记忆。
- 反馈记忆。
- 记忆治理操作。

避免将内部数据库 CRUD 直接暴露给工作模型。

## R15-3：Shared Bridge 职责

**最终选择：方案 B——统一客户端网关**

多个 Host 连接同一个本地 Shared Bridge。

Bridge 负责本地访问、认证、记忆副本和远端同步。

Host 不需要分别维护一套完整的远端连接逻辑。

## R15-4：客户端集成方式

**最终选择：方案 B——MCP + Hook + Skill，按客户端能力启用**

根据各 AI Host 的能力选择接入方式。

- MCP：提供记忆工具。
- Hook：负责生命周期事件和运行时注入。
- Skill：提供使用规则、操作指引和行为约束。

不要求每个 Host 必须支持所有接入机制。

---

# 十七、R16：Monorepo 与本地 Bridge

## R16-1：Monorepo 组织

**最终选择：方案 B——Workspace Monorepo**

所有客户端插件和核心模块位于同一个仓库。

使用 Workspace 管理多个包及共享依赖。

## R16-2：Adapter 内部架构

**最终选择：方案 B——共享 Adapter SDK + 客户端专属实现**

共享部分提供统一接口、协议和公共工具。

每个客户端拥有独立 Adapter 实现。

避免将客户端特有行为混入公共核心。

## R16-3：Shared Bridge 运行架构

**最终选择：方案 A**

采用常驻 Shared Bridge Daemon。

Bridge 在本地持续运行，多个 AI Host 连接同一个实例。

负责本地记忆副本、访问网关和同步。

## R16-4：构建与发布

**最终选择：方案 B——统一源码，独立构建和发布**

所有模块共享源码和依赖管理，但不同客户端插件可以独立构建和发布。

一个客户端更新不要求其他客户端同步更新。

## R16-5：同步机制

**最终选择：方案 B**

采用周期性同步，并结合必要的条件触发同步。

不是所有操作都必须实时访问 Server。

## R16-6：本地数据存储

**最终选择：方案 B**

采用 SQLite + 持久化队列 + 本地记忆副本 + 有限运行缓存。

本地数据库维护远端记忆的逻辑副本，以减少远端 Recall 延迟。

持久化队列负责处理需要等待网络恢复的操作。

运行缓存具有容量和生命周期限制，不能无限增长。

# 十八、R17：记忆历史与容量治理

## R17-1：Session 原始数据保留策略

**最终选择：方案 B——热数据 + 限期归档 + 重要事件长期保留**

Session 原始事件采用分层保留。

近期活跃数据保留在热存储中。

一般历史事件限期归档。

具有长期工程价值的重要事件允许长期保留。

## R17-2：Candidate Memory 生命周期

**最终选择：方案 B——保留审核记录，按状态清理候选内容**

保留候选记忆的审核记录和必要元数据。

根据候选状态及其生命周期清理不再需要的内容。

不得因为清理候选正文而丢失重要审核历史。

## R17-3：长期记忆自动维护

**最终选择：方案 B——后台自动分析，形成候选治理操作**

后台定期分析长期记忆。

可以形成以下候选治理操作：

- 过时识别。
- 重复识别。
- 冲突识别。
- 合并建议。
- 替代建议。
- 重新验证建议。

后台自动分析不直接绕过审核和治理流程。

## R17-4：长期记忆版本与历史保留

**最终选择：方案 B——不可变版本 + 当前版本指针**

正式记忆采用不可变版本。

更新时创建新版本，并更新当前版本指针。

历史版本保留，以支持追溯和历史 Recall。

## R17-5：本地副本变更与删除传播

**最终选择：方案 C——增量变更流 + 定期全量校验**

通过增量变更流同步远端数据变更。

定期执行全量校验，发现不一致时进行修复。

支持记忆更新、删除、替代、归档等状态传播。

## R17-6：存储容量预算与自动清理

**最终选择：方案 B——软限制 + 硬限制 + 优先级清理**

设置软容量限制和硬容量限制。

达到软限制后触发清理建议或自动维护。

达到硬限制时限制非关键数据继续增长。

按照数据优先级清理，而不是简单按照文件创建时间删除。

# 十九、R18：Recall 与上下文组装

## R18-1：Recall 执行位置

**最终选择：方案 A——Local-first**

优先使用本地 Memory Replica 执行 Recall。

只有本地无法满足查询、缺少必要数据或需要远端补充时，才访问 Server。

降低远端查询延迟，并支持一定程度的离线使用。

## R18-2：记忆检索技术架构

**最终选择：方案 C——混合检索 + 实体关系扩展**

采用多种检索方式组合：

- 全文检索。
- 向量语义检索。
- 结构化过滤。
- 实体匹配。
- 关系扩展。

不将单一向量检索作为唯一 Recall 机制。

按阶段实现，先建立可靠的基础检索，再增加实体关系扩展。

## R18-3：Recall 检索流水线

**最终选择：方案 B——多阶段检索 + 可选模型重排**

Recall 采用多阶段处理：

1. 解析查询。
2. 根据上下文和权限确定检索范围。
3. 执行多路检索。
4. 合并候选结果。
5. 去重和过滤。
6. 必要时使用模型重排。
7. 生成最终结构化记忆结果。

模型重排是可选能力，不要求每次 Recall 都调用 LLM。

## R18-4：Pinned Memory 作用域

**最终选择：方案 C——Global + Project + Host + Session**

Pinned Memory 支持四个作用域：

- Global：跨项目通用知识。
- Project：项目相关记忆。
- Host：特定 AI Host 的工作习惯和上下文。
- Session：当前会话需要持续保持的上下文。

不同作用域需要明确优先级和授权边界。

## R18-5：Dynamic Projection 生成与更新

**最终选择：方案 C——基线 Projection + 动态增量更新**

先生成稳定的基线 Projection。

随着项目、Session 和任务上下文变化，再动态生成增量内容。

不要求每次发生变化都重新计算全部 Projection。

## R18-6：Context Budget 与 Token 分配

**最终选择：方案 C——分层预算 + 动态调整**

上下文预算分层管理。

根据记忆重要性、作用域、任务相关性和当前 Token 限额动态调整。

优先保证关键记忆和必要约束。

不能因为大量低价值记忆挤占预算而丢失关键工程知识。

## R18-7：Recall 输出格式

**最终选择：方案 C——结构化记忆 + 自然语言呈现**

Recall 内部保留结构化数据。

向工作模型提供便于理解的自然语言内容，同时保留：

- Memory ID。
- 来源。
- 可信度。
- 适用条件。
- 版本状态。
- 相关关系。

不将结构化数据和自然语言表达割裂。

## R18-8：模型遵循与反馈闭环

**最终选择：方案 C——注入 + 行为评估 + 反馈闭环**

不仅负责把记忆注入模型上下文，还要评估模型是否实际使用了相关记忆。

通过行为评估和反馈机制持续改善：

- Recall 结果质量。
- 注入内容。
- 记忆选择。
- 运行时提示。
- 记忆使用策略。

不把提示词注入本身当作模型遵循的保证。

# 二十、R19：记忆沉淀和知识治理

## R19-1：Remember 输入来源与触发机制

**最终选择：方案 B——显式 Remember + 工作事件触发**

两种入口：

- 工作模型主动 Remember。
- 工作事件触发后台整理。

事件只提供候选知识素材，不直接进入正式记忆。

## R19-2：工程知识分类体系

**最终选择：方案 C——固定一级类型 + 自由标签 + 实体关系**

采用固定一级知识类型：

- Concept：技术原理。
- Practice：工程实践。
- Architecture：架构决策。
- Troubleshooting：故障案例。
- Constraint：技术约束。
- Procedure：操作流程。
- Reference：技术参考。

在此基础上允许自由标签和实体关系扩展。

## R19-3：跨项目知识抽象与复用

**最终选择：方案 C——生成抽象候选，审核后晋升 Global**

跨项目知识不能简单复制或直接提升为 Global。

先提炼具有通用价值的抽象候选。

审核其通用性、适用范围、证据和限制条件后，再晋升 Global。

保留原始项目记忆及来源关系。

## R19-4：记忆来源、证据与可信度

**最终选择：方案 B——结构化 Provenance + 可信度信息**

每条重要记忆应具有结构化来源和证据。

包括：

- Source。
- Source Reference。
- Evidence。
- Verification Status。
- Confidence。
- Applicability。
- Limitations。
- Last Verified。

模型自评置信度不能替代真实工程验证。

## R19-5：Candidate Memory 质量检查

**最终选择：方案 C——规则检查 + LLM 语义检查**

规则检查负责确定性验证。

LLM 负责语义层面检查：

- 内容是否完整。
- 是否存在歧义。
- 是否缺少必要适用条件。
- 是否存在潜在矛盾。
- 是否具有长期保存价值。

两者共同形成审核建议。

## R19-6：记忆冲突与合并数据模型

**最终选择：方案 B——独立记忆 + 显式关系**

冲突双方首先作为独立记忆保存。

通过明确关系表达：

- Supports。
- Contradicts。
- Supersedes。
- Refines。
- DuplicateOf。
- DerivedFrom。
- RelatedTo。

合并时产生新候选，不直接覆盖已有正式记忆。

## R19-7：正式记忆写入与审核流程

**最终选择：方案 B——Transactional Outbox + 幂等写入 + Receipt**

审核通过后，将正式写入任务放入 Transactional Outbox。

通过稳定幂等键执行 Provider 写入。

使用 Receipt 记录操作及结果。

写入成功后确认持久化状态。

发生超时或失败时，通过结果核对确定是否已经执行，避免重复写入。

## R19-8：知识过时识别与重新验证

**最终选择：方案 C——时间 + 事件双重触发**

根据知识的时间特征和外部事件触发重新验证。

例如：

- 软件版本变化。
- 项目架构变化。
- 技术方案被替代。
- 外部技术规范更新。
- 关键硬件平台变化。
- 长期未验证的技术结论。

知识重新验证状态包括：

- Valid。
- ReviewDue。
- SuspectedStale。
- Superseded。
- Invalidated。

重新验证不等于直接失效。

# 二十一、R20：工程化与可靠性

## R20-1：核心模块依赖架构

**最终选择：方案 B——领域模块化 + 分层依赖**

按业务领域组织模块。

每个模块内部再划分 Domain、Application、Ports 等职责。

模块之间通过明确契约交互。

不采用无边界的传统分层混合结构，也不在第一阶段采用动态插件化微内核。

## R20-2：Mnemon Provider 适配策略

**最终选择：方案 C——官方接口优先，能力缺口通过适配层解决**

优先使用 Mnemon 官方 API。

不直接依赖其内部数据库 Schema。

Provider 必须声明能力。

能力缺口优先通过：
- 组合已有官方接口。
- Mneme 自身治理层补足。
- 向上游提出能力增强需求。

解决。

## R20-3：数据所有权与职责划分

**最终选择：方案 C——记忆数据与治理数据分离**

Mnemon 负责正式记忆及其原生实体关系和检索能力。

Mneme 负责：

- Candidate Memory。
- 审核记录。
- Provenance 扩展。
- Task / Pipeline Run / Receipt。
- 同步状态。
- 生命周期治理。

Revision 快照和当前版本指针的最终权威需要在详细设计中确定。

## R20-4：HTTP / MCP 接口契约管理

**最终选择：方案 C——Contract-first，统一 Schema 驱动**

以统一 TypeScript Schema 作为契约源。

HTTP 映射为 OpenAPI。

MCP 映射为工具 Schema。

Application Core 仍然是唯一业务执行入口。

## R20-5：任务与 Pipeline 故障恢复

**最终选择：方案 B——持久化状态机 + 检查点 + 自动恢复**

任务状态、执行阶段、检查点、重试次数和错误信息持久化。

服务重启后恢复未完成任务。

无法自动恢复的任务进入人工介入状态。

## R20-6：本地副本同步一致性

**最终选择：方案 C——快照初始化 + 增量批处理 + 定期校验**

首次通过一致性快照建立本地副本。

后续采用增量批量同步。

数据和 Cursor 在同一个本地数据库事务中提交。

定期全量校验，不一致时修复或重建。

支持 Tombstone、授权撤销、游标失效和索引修复。

## R20-7：安全与权限架构

**最终选择：方案 B——Bridge 身份 + Host 身份 + 作用域授权**

Bridge 拥有独立身份和凭据。

每个 AI Host 拥有独立身份。

Host 通过本地 Bridge 注册和认证。

Bridge 通过独立凭据连接 Server。

支持独立撤销、凭据轮换、TLS 和授权审计。

遵循 R7 Strict Grants。

## R20-8：配置管理与运行诊断

**最终选择：方案 B——结构化配置 + 统一诊断体系**

配置采用分层管理：

- 默认配置。
- 配置文件。
- 环境变量。
- 启动参数。

启动时执行 Schema 校验。

诊断覆盖：
- 结构化日志。
- Health Check。
- Readiness Check。
- Worker 状态。
- Task Queue 状态。
- Provider 状态。
- 同步延迟和 Cursor。
- 数据库和 Blob 状态。
- Model Gateway 状态。
- Trace ID。

预留 OpenTelemetry。

## R20-9：测试架构

**最终选择：方案 B——分层测试体系**

包括：

- Unit Test。
- Integration Test。
- Contract Test。
- E2E Test。
- Reliability Test。

选择性吸收属性测试、模糊测试、并发压力测试和故障注入。

重点保证 Provider、同步、任务恢复和多模块交互的可靠性。

## R20-10：数据迁移与软件升级

**最终选择：方案 B——版本化 Migration + 自动备份 + 恢复**

Mneme 和 Bridge 分别管理数据库 Migration。

重要升级前执行备份。

Migration 版本化管理。

升级失败时禁止进入正常业务状态。

优先向前修复，不依赖复杂的自动降级脚本。

Mnemon 内部数据库迁移由 Mnemon 自己负责，Mneme 不直接修改其内部 Schema。

## R20-11：部署与进程管理

**最终选择：方案 B——Server 系统服务 + Bridge 用户级后台进程**

Server：
- Linux 原生部署。
- systemd 管理。
- Worker 暂时在 Server 进程内部运行。

Bridge：
- Windows 用户级后台进程。
- Linux systemd --user。
- 多个 Host 共用一个 Bridge。

预留统一服务管理抽象，但第一阶段不额外建设复杂的跨平台服务管理体系。

## R20-12：组件版本兼容

**最终选择：方案 C——SemVer + Capability Negotiation**

所有组件独立版本管理。

连接时协商协议版本和能力。

覆盖：
- Server。
- Bridge。
- Adapter SDK。
- Host Adapter。

能力声明不代表获得授权。

必需能力缺失时明确拒绝相关功能，不允许静默降级造成数据不一致。

# 二十三、总体约束

以上所有决策共同构成 Mneme 项目的架构基线。

实施过程中必须遵循：

1. 已确认的决策不得擅自改变。
2. 不允许将 Mnemon 和 dsh-mnemon 的能力混为一谈。
3. 不允许在未核查上游接口前冻结 Provider Adapter。
4. 不允许在未核查数据权威边界前冻结数据库 Schema。
5. 不允许记忆系统自行寻找副脑模型。
6. 不允许无限期保存全部 Session 原始数据。
7. 不允许未经审核的候选记忆直接进入正式记忆。
8. 不允许通过覆盖方式丢失正式记忆历史。
9. 不允许本地副本与远端权威记忆长期失去一致性。
10. 不使用 Docker 作为部署前提。

**本文件是 P0-R20 已确认决策的统一整理版，后续详细设计必须以此为基础。**
